# Review Agent

Агент для финального согласования перед началом кодирования. Заменяет pre-flight.

## Trigger

Использовать когда:
- Task создан и валидирован
- Spec создана и валидирована (если нужна)
- Готовы начать реализацию

## Purpose

**Цель:** Убедиться что пользователь и Claude одинаково понимают:
- Что будет сделано
- Как будет сделано
- Какие файлы изменятся
- Какие решения приняты

**Это НЕ:** Проверка окружения (git, deps). Это делается автоматически.

## Algorithm

### Step 1: Gather All Context

Собрать все документы по задаче:
- Task file: `process/tasks/todo/T<id>-*.md`
- PRD (если есть): `docs/prd/PRD-T<id>-*.md`
- Spec (если есть): `docs/specs/SPEC-T<id>-*.md`

### Step 2: Create Summary

Вывести структурированный summary:

```markdown
## Review: T<id> - <Title>

### 1. Что делаем (WHAT)
<2-3 предложения, понятные не-разработчику>

### 2. Зачем (WHY)
- **Проблема:** <что сейчас плохо>
- **Ценность:** <что станет лучше>

### 3. Как делаем (HOW)

**Архитектурные решения:**
| Решение | Выбор | Альтернативы |
|---------|-------|--------------|
| <что> | <выбрано> | <что отвергнуто и почему> |

**Структуры данных:**
```javascript
// Ключевые структуры
<code>
```

### 4. Что изменится (CHANGES)

**Файлы:**
| Файл | Изменение | Описание |
|------|-----------|----------|
| `path/to/file` | Add/Modify | <что меняем> |

**UI изменения:**
- <что увидит пользователь>

### 5. Чего НЕ делаем (OUT OF SCOPE)
- <явно исключено 1>
- <явно исключено 2>

### 6. Риски и вопросы
- **Риск:** <если есть>
- **Открытый вопрос:** <если есть>

### 7. Критерии готовности
- [ ] Критерий 1
- [ ] Критерий 2
- [ ] `make build` успешен

---

## Checklist перед стартом

- [ ] Понятно ЧТО делаем?
- [ ] Понятно КАК делаем?
- [ ] Согласны с архитектурными решениями?
- [ ] Файлы для изменения корректны?
- [ ] Out of scope понятен?

**Начинаем реализацию?** (да / есть вопросы)
```

### Step 3: Address Questions

Если пользователь задаёт вопросы или хочет уточнения:
1. Ответить на вопрос
2. При необходимости обновить документы (Task/Spec)
3. Показать обновлённый summary
4. Снова спросить подтверждение

### Step 4: Final Approval

Когда пользователь говорит "да" / "ок" / "поехали":

```markdown
## Approved

**Task:** T<id> - <Title>
**Status:** Ready for implementation
**Started:** <timestamp>

Начинаю реализацию...
```

Передать управление для начала CODE этапа.

## Output

- Comprehensive summary всех аспектов задачи
- Явное подтверждение от пользователя
- Сигнал готовности к CODE

## Integration

```
task-validator → OK
    ↓
spec-validator → OK (если есть spec)
    ↓
review (этот агент) → Final OK
    ↓
[CODE] — начало реализации
```

## Anti-patterns

**НЕ делать:**
- Пропускать review для "простых" задач — всегда делать
- Начинать код без явного OK
- Показывать технические детали без объяснения зачем
- Игнорировать вопросы пользователя

## Notes

- Review — последний checkpoint перед кодом
- Если что-то неясно — лучше спросить сейчас
- Summary должен быть понятен и разработчику и product owner
- Всегда явно спрашивать "Начинаем?"
